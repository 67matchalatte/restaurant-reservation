# ADR-002: Проверка занятости столика — транзакция с блокировкой на уровне БД

**Статус:** принято (21.10.2026)

## Контекст
- ФТ-5: система должна проверять, что столик свободен на указанное время.
- АЗТ-2: до 50 одновременных запросов бронирования.
- Замечание ревью №35: связь «Столик — Бронь» должна учитывать время.
- Риск двойной брони при гонке запросов (два гостя бронируют один столик одновременно).

## Решение
Проверку занятости и вставку брони выполнять **в одной транзакции** с блокировкой (в SQLite — `BEGIN IMMEDIATE`; в PostgreSQL — `SELECT ... FOR UPDATE`).

Псевдокод:
```BEGIN IMMEDIATE;
SELECT 1 FROM bookings WHERE table_id=? AND date=? AND time=? AND status IN ('ОЖИДАЕТ','ПОДТВЕРЖДЕНА');
IF EXISTS -> ROLLBACK, вернуть 409;
INSERT INTO bookings (...);
COMMIT;
```

## Отвергнутые альтернативы
- **Проверка на уровне приложения без транзакции:** гонка → двойная бронь (нарушает ФТ-5).
- **Уникальный индекс на (table_id, date, time):** не работает, т.к. отменённые брони должны освобождать слот (статус меняется).

## Последствия
- (+) Гарантия отсутствия двойной брони даже при 50 одновременных запросах.
- (−) Транзакции сериализуются; при росте нагрузки потребуется очередь/пул (см. ADR-003 — план).
- Связь «Столик — Бронь» реализуется через атрибут времени, а не отдельным классом (закрывает замечание №35).
