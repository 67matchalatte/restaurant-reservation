# Архитектурное ревью по качественным сценариям (ЛР-5, шаг 5)

Дата: 21.10.2026. Участники: Буркова Т.В., Исаева А.Д., Гималова П.А.

## Сценарий 1. Падение ключевого контейнера (API-сервер)

**Стимул:** API-сервер упал в 19:00 (пик бронирований).
**Ожидание (АЗТ-3):** система восстанавливается, гость видит понятную ошибку, брони не теряются.

**Анализ:**
- Фронтенд (SPA) продолжает работать, показывает «Сервис недоступен, попробуйте позже».
- Брони хранятся в БД (SQLite/PostgreSQL) — не теряются при падении API.
- Автоперезапуск: systemd/Docker `restart: always` → восстановление за ~5–10 с.
- Во время недоступности новые брони не создаются; уже созданные — в БД.

**Вывод:** архитектура устойчива к падению API; риск потери данных отсутствует.
**Отражение в ADR:** ADR-003 (последствия: автоперезапуск). **Риск принят.**

## Сценарий 2. Десятикратный рост нагрузки (500 одновременных запросов)

**Стимул:** нагрузка выросла с 50 до 500 одновременных запросов бронирования.
**Ожидание (АЗТ-2):** система не падает, время ответа деградирует плавно.

**Анализ:**
- SQLite с `BEGIN IMMEDIATE` сериализует транзакции → при 500 запросах очередь, время ответа растёт (риск таймаутов).
- Узкое место: блокировка БД при проверке занятости (ADR-002).
- Меры: (1) включить WAL-режим SQLite; (2) кэшировать каталог (АЗТ-1); (3) план миграции на PostgreSQL с `SELECT ... FOR UPDATE` (ADR-001).

**Вывод:** при 10× росте монолит деградирует, но не падает.
**Отражение в ADR:** ADR-002 (принятый риск), ADR-001 (план миграции).
**Корректировка:** в ADR-002 добавлен пункт «при нагрузке > 100 запросов — миграция на PostgreSQL».

**Стимул:** один участник уходит, новый вступает в проект.
**Ожидание:** новый участник понимает архитектуру за 1 день.

**Анализ:**
- C4-контекст и контейнеры + ADR + диаграмма последовательностей = полная картина.
- README ссылается на docs/architecture/.

**Вывод:** архитектура документирована достаточно для передачи.
**Отражение:** все ADR + C4 + sequence.
